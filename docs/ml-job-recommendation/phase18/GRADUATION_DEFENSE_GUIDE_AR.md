# دليل مناقشة مشروع ML Job Recommendation

## 1. شرح الفكرة خلال دقيقة

النظام يوصي الباحث عن عمل بالوظائف المناسبة من بين الوظائف التي سمح بها
Laravel أولًا. يجمع Laravel الحقائق المهنية المسموح بها، ثم يطلب من خدمة ML
داخلية ترتيب الوظائف. تعيد الخدمة درجة عرض وأسبابًا تفسيرية، وبعدها يتحقق
Laravel من الهوية والإصدارات ويطبّق الترتيب النهائي ويحفظ النتيجة. إذا تعطلت
خدمة ML يبقى النظام متاحًا باستخدام MatchingService 2.0.

هذه توصية مساعدة فقط. النظام لا يقبل المتقدم، ولا يرفضه، ولا يتخذ قرار توظيف.

## 2. المشكلة التي يحلها

المعادلات الثابتة مفهومة وسهلة، لكنها قد لا تمثل العلاقات غير الخطية بين
خبرات الباحث ومهاراته وخصائص الوظيفة. الهدف هو تحسين ترتيب الوظائف المناسبة
مع الحفاظ على قواعد العمل والأمان والتفسير والاستمرارية.

## 3. لماذا استخدمنا ML بدل Formula فقط

XGBRanker يستطيع تعلم تفاعلات بين مجموعة كبيرة من الخصائص وترتيب العناصر داخل
كل مجموعة باحث عن عمل. لكنه لم يستبدل Formula كليًا؛ بقي MatchingService 2.0
خط أساس ووسيلة fallback. هذا يسمح بالمقارنة والاستمرارية ويقلل أثر تعطل خدمة
ML.

## 4. لماذا أبقينا MatchingService Fallback

الـfallback يضمن أن endpoint العامة لا تتوقف عند timeout أو خطأ شبكة أو
مشكلة token أو Bundle أو Contract. يسجل Laravel سببًا آمنًا ويستخدم
`matching_v2_fallback`. العيب التشغيلي هو أن نجاح HTTP قد يخفي تعطل ML، لذلك
يجب مراقبة نسبة fallback.

## 5. لماذا Laravel مصدر Eligibility

Laravel يملك قاعدة البيانات وقواعد الأعمال وحالة الشركة والوظيفة وطلبات
التقديم السابقة والصلاحيات. نقل Eligibility إلى Python سيكرر القواعد ويزيد
احتمال التناقض. لذلك Python يرتب فقط القائمة التي أرسلها Laravel ولا يكتشف
مستخدمين أو وظائف من تلقاء نفسه.

## 6. كيف صممنا Dataset الاصطناعية

أنشأنا Dataset حتمية ذات إصدار ثابت تضم 180 باحثًا اصطناعيًا و180 وظيفة
و10,800 زوج باحث–وظيفة. لكل باحث 60 وظيفة مرشحة مع labels وسيناريوهات متنوعة
وضوضاء مضبوطة. استُبعدت الحقول الحساسة والديموغرافية من خصائص النموذج.

البيانات الاصطناعية مناسبة لإثبات الهندسة وقابلية التكرار، لكنها لا تمثل
الواقع كاملًا ولا تثبت جودة النموذج على مستخدمين حقيقيين.

## 7. لماذا استخدمنا Group Split

قسمنا البيانات حسب الباحث، لا حسب الصف. جميع أزواج الباحث الواحد تبقى في
Train أو Validation أو Locked Test فقط. هذا يمنع أن يرى النموذج الباحث نفسه
أثناء التدريب والاختبار، ويقلل data leakage.

التقسيم هو:

- Train: 126 باحثًا و7,560 زوجًا.
- Validation: 27 باحثًا و1,620 زوجًا.
- Locked Test: 27 باحثًا و1,620 زوجًا.

## 8. لماذا استخدمنا XGBRanker

المشكلة Ranking وليست تصنيفًا ثنائيًا فقط. XGBRanker يتعلم ترتيب الوظائف داخل
مجموعة الباحث، يتعامل مع العلاقات غير الخطية، ويعمل جيدًا مع بيانات tabular.
استخدمنا إعدادًا مضبوطًا ومحدودًا، واختير T06 على Validation فقط.

## 9. معنى NDCG وMRR ببساطة

**NDCG** يقيس جودة ترتيب النتائج مع إعطاء أهمية أكبر للوظائف المناسبة التي
تظهر في أعلى القائمة. الدرجة الأعلى تعني ترتيبًا أفضل مقارنة بالترتيب
المثالي.

**MRR** ينظر إلى موضع أول نتيجة مناسبة. إذا ظهرت أول وظيفة مناسبة في المركز
الأول تكون القيمة أفضل من ظهورها في المركز الخامس.

هذه metrics لقياس ranking على Dataset محددة، وليست ضمانًا لجودة التوظيف.

## 10. معنى SHAP

SHAP يوزع فرق model score على الخصائص أو مجموعات الخصائص. نستخدمه لإظهار
العوامل التي رفعت أو خفضت score لهذا الزوج. ثم نحول المجموعات المسموح بها إلى
reason codes مستقرة.

SHAP Attribution ليست Causality. لا يجوز القول إن العامل سبب النجاح أو سبب
قرارًا بشريًا.

## 11. لماذا Score ليست Probability

`display_score` ناتجة عن تحويل محدد باستخدام نطاق Validation للنموذج المختار
ثم قصها إلى 0–100. هي مؤشر عرض للمقارنة والترتيب، وليست احتمال قبول، أو نجاح،
أو ملاءمة مؤكدة، ولا يجوز تفسير 80 على أنه احتمال 80%.

## 12. الخصوصية

Laravel يرسل حقائق مهنية مسموحًا بها ومرجعًا opaque، ولا يرسل الاسم أو البريد
أو الهاتف أو CV أو بيانات المقابلات والتقييمات. يوجد guard في Laravel
وdenylist متكرر في FastAPI. لا تُسجل request bodies أو tokens أو provider
responses. اختبارات Phase 17 بحثت عن markers حساسة وكانت النتيجة صفر تسرب.

## 13. الأمان

- endpoint العامة محمية بـSanctum وmiddleware الموجودة.
- endpoint الداخلية محمية بـservice token قابلة للتدوير.
- الأخطاء تستخدم codes آمنة بلا stack traces أو payload.
- الحاوية تعمل كمستخدم غير root وبصلاحيات وfilesystem مقيدة.
- الإصدارات مترابطة ويُرفض أي Contract غير متوافق.
- الأسرار تبقى في secret manager أو environment، لا في المستودع.

## 14. Cache وPersistence

الطلب الأول يحسب النتيجة ويحفظ `recommendation_runs` و
`recommendation_items`. Cache لا تحفظ payload كاملة؛ تحفظ pointer صغيرة إلى
run مع context hash وlimit وexpiry. إذا مُسحت Cache يستطيع Laravel إعادة
استخدام النتيجة الدائمة من Database. إذا تغير Profile أو Job أو Eligibility
يتغير context hash ولا تُستخدم النتيجة القديمة.

## 15. Docker

الصورة الحالية هي `workeyx/ml-recommendation:0.2.0-phase16`. تعمل على
Python 3.12.10 بمستخدم UID/GID 10001 وعامل واحد. root filesystem read-only،
والـhealthcheck تفصل liveness عن readiness، وتتحقق الخدمة من Bundle عند
startup. Phase 18 لم تُعد بناء الصورة ولم تنشرها Production.

## 16. Failure Handling

اختبرنا connection refused وtimeout و401 و422 و429 و500 و503 وbody فارغة
وJSON غير صالح وأخطاء versions وrequest ID وpredictions وranks وscores
وreasons وإغلاق الاتصال. كل حالة قامت بمحاولة provider واحدة فقط ثم fallback
آمن بلا retry مخفي وبلا تفاصيل حساسة في public API.

## 17. حدود المشروع

- النموذج مدرب على Synthetic data.
- لا توجد fairness certification.
- لا يوجد Production deployment أو Production load test.
- concurrency المحلية محدودة وليست benchmark إنتاجية.
- لا توجد dashboards أو alerting أو drift automation في Production.
- لا يوجد CI/CD لهذه الحزمة.
- fallback قد يخفي outage ما لم تتم مراقبته.
- AI مساعد وليس صاحب القرار.

## 18. ما الذي سنفعله ببيانات حقيقية مستقبلًا

نحتاج consent وdata governance وتعريف labels ومراجعة الجودة والتحيز، ثم Group
split جديد وسياسة retraining مضبوطة. يجب مقارنة baseline والنموذج، وإجراء
fairness evaluation ومراجعة بشرية، وإنشاء version جديدة منفصلة، ثم deployment
تدريجي مع monitoring وrollback. لا نعيد استخدام Locked Test الحالية لاتخاذ
قرارات tuning جديدة.

## 20. إجابات دقيقة مختصرة

**لماذا لا توجد Database في Python؟**

لمنع تكرار business rules ولإبقاء Laravel مصدر الحقيقة الوحيد.

**ماذا يحدث عند تعطل ML؟**

Laravel يستخدم MatchingService 2.0 ويسجل code آمنة وتبقى endpoint متاحة.

**هل score احتمال؟**

لا. هي relevance display score للتحويل والترتيب فقط.

**هل SHAP سبب حقيقي؟**

لا. هي attribution داخل النموذج وليست causal explanation.

**كيف منعتم leakage؟**

بـGroup split حسب candidate وبمنع استخدام Locked Test في التدريب والتuning.

**لماذا Synthetic data؟**

لإثبات pipeline كاملة بصورة حتمية وآمنة؛ ولا ندّعي أنها تمثل الواقع كاملًا.

**من يحدد Eligibility؟**

Laravel وحده قبل إرسال candidate pool إلى ML.

**كيف حميتم الخصوصية؟**

بعقد professional facts، guards وdenylist، safe logs، واختبارات تسرب.

**لماذا XGBRanker؟**

لأن المطلوب ترتيب jobs داخل مجموعة، لا توقع label منفرد فقط.

**ماذا يلزم قبل Production؟**

بيانات حقيقية محكومة، fairness، monitoring، alerting، secrets، scanning،
load testing، CI/CD، وdeployment تدريجي.

**هل أثبتم أن النموذج عادل؟**

لا. لم تُجر fairness evaluation على بيانات حقيقية.

**هل AI يقرر التوظيف؟**

لا. يقدم توصيات وأسبابًا مساعدة، والقرار البشري خارج هذا النظام.
